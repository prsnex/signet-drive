# Test Vector Category 02: AES-256-GCM round-trips

**Layer:** 1 + 2 (spec + concrete inputs; the single-PUT envelope and the multipart chunk envelope are golden-filled)
**Spec source:** [Envelope Format](../Signet-Drive-Envelope-Format.md) sections 4.1 (single-PUT), 4.2 (multipart), 7.3 (encrypted names), 8 (wrap envelope)
**External standards:** NIST SP 800-38D (AES-GCM), RFC 5116 (AEAD)

---

## Why this vector exists

AES-256-GCM is used in three places: (a) file ciphertext encryption (Envelope Format sections 4.1 and 4.2), (b) wrap-key envelope encryption (section 8, which encrypts the human's KEM private material as `wrapped_kem_privkey_blob`), and (c) encrypted-name envelopes (section 7.3, which encrypt file and folder names with the per-share-folder metadata key).

If implementations disagree on AES-GCM parameter encoding (IV length, AAD content, tag position, byte ordering), ciphertexts produced by one component fail to decrypt in another. This vector pins the AES-GCM parameters and AAD constructions.

## AES-256-GCM parameters

| Parameter | Value | Spec |
|---|---|---|
| Algorithm | AES-256-GCM | `alg: "A256GCM"` per RFC 7518 section 5.3 |
| Key length | 32 bytes (256 bits) | NIST SP 800-38D |
| IV (nonce) length | 12 bytes (96 bits) | NIST SP 800-38D recommended length for GCM |
| Tag length | 16 bytes (128 bits) | NIST SP 800-38D full tag |
| Tag position | Appended after ciphertext | Envelope Format section 4.1 layout |

## AAD constructions per use

| Use | AAD bytes | Notes |
|---|---|---|
| Single-PUT file ciphertext | `file_id` raw 16 bytes (UUID) | Envelope Format section 4.1 |
| Multipart file chunk ciphertext | `file_id` (16) \|\| `uint32_be(chunk_index)` (4) \|\| `is_last` (1) = 21 bytes | Envelope Format section 4.2; `is_last` is `0x01` for the terminal chunk, `0x00` otherwise |
| Wrap envelope (`wrapped_kem_privkey_blob`) | ASCII bytes of `"signet-drive-kem-wrap-v1"` (24 bytes) | Envelope Format section 8.3 |
| Encrypted-name envelope | `root_folder_id` (16) \|\| `target_id` (16) = 32 bytes | Envelope Format section 7.3 |

The metadata-KEY envelope itself carries no AAD: it is AES Key Wrap (RFC 3394), which has no AAD parameter; its folder binding rides the Concat-KDF `PartyVInfo` instead (Envelope Format section 7.2).

## Test cases

### TC02-01: Single-PUT file encryption (small file, known IV/AAD)

**Setup:** a client encrypts a small plaintext file; the envelope is produced per Envelope Format section 4.1.

**Inputs:**

| Parameter | Value |
|---|---|
| Plaintext | UTF-8 bytes of `"hello signet"` (12 bytes: `68 65 6c 6c 6f 20 73 69 67 6e 65 74`) |
| DEK (AES-256 key) | 32 bytes; deterministic for testing: SHA-256 of ASCII `"test-dek-tc02-01"` |
| IV (12 bytes) | NOT random for testing; deterministic: lowercase hex `0102030405060708090a0b0c` |
| AAD | `file_id` = `00000000-0000-4000-8000-000000000111` raw 16 bytes (`00 00 00 00 00 00 40 00 80 00 00 00 00 00 01 11`) |

**Expected envelope layout (per Envelope Format section 4.1):**

```
[magic 0x01] [alg 0x01] [12-byte IV] [12-byte ciphertext] [16-byte tag]   = 1 + 1 + 12 + 12 + 16 = 42 bytes total
```

**Expected output:** the golden bytes live in [`golden/wrap-chain.json`](golden/wrap-chain.json) under `file_envelope_cat02`, generated by [`gen/`](gen/) via Node WebCrypto (independent of the RustCrypto implementation under test).

**Round-trip property:** decrypt(envelope, DEK, AAD) recovers the plaintext.

### TC02-02: Multipart file chunk

**Setup:** as TC02-01 except the multipart envelope per section 4.2; the AAD includes the chunk index and the `is_last` byte.

**Inputs (illustrative):**

| Parameter | Value |
|---|---|
| Plaintext (one chunk) | 16-byte test pattern: `00 11 22 33 44 55 66 77 88 99 aa bb cc dd ee ff` |
| DEK | Same as TC02-01 |
| IV (12 bytes) | HKDF-derived per section 4.2: `HKDF-SHA-256(DEK, empty salt, "signet-drive-multipart-iv-v1" || chunk_index_be, 12)` |
| AAD | `file_id` (16) \|\| `uint32_be(5)` (4) \|\| `is_last = 0x00` (1) = 21 bytes, for a non-terminal chunk at index 5. The decryptor derives `is_last` from the externally supplied chunk count; the AAD authenticates it. |

**Committed golden:** [`golden/chunk-envelope.json`](golden/chunk-envelope.json) (generated by `gen/chunk_envelope_gen.mjs`) pins the full chain for a non-terminal chunk (index 7 of 10) and is consumed by both the Rust and web test suites, so three lineages must agree byte-for-byte.

**Verification:** a wrong AAD (wrong chunk index; wrong `is_last`) MUST fail tag verification. This is the cross-chunk replay, reordering, and truncation protection; testing it requires explicit fail cases.

### TC02-03: Wrap envelope (`wrapped_kem_privkey_blob`)

**Setup:** per Envelope Format section 8.4, the browser wraps the private material with W (the HKDF-derived wrap key from [Test Vector Category 01](01-hkdf-sha256-prf-derivation.md)).

**Inputs:**

| Parameter | Value |
|---|---|
| Plaintext | The 32-byte ECDH P-256 private scalar (the secret half of the keypair). For testing: deterministic test private key `01 02 03 04 ... 1f 20` (32 bytes counting up; a valid P-256 private scalar; verify it is below the curve order n). |
| W (wrap key) | Per Category 01 TC01-02 (deterministic from the designated reference PRF output). |
| IV (12 bytes) | Random per wrap; for the testing fixture: `0102030405060708090a0b0c` |
| AAD | ASCII bytes of `"signet-drive-kem-wrap-v1"` (24 bytes); see Category 01 TC01-01 for the byte-level encoding |

**Expected envelope structure (JSON, per Envelope Format section 8.3):**

```json
{
  "alg": "A256GCM",
  "iv": "<base64url-no-pad of 12-byte IV>",
  "ct": "<base64url-no-pad of ciphertext>",
  "tag": "<base64url-no-pad of 16-byte tag>"
}
```

**Expected values:** pinned in [`golden/kem-wrap.json`](golden/kem-wrap.json) (see Category 01, Layer 2 status).

**Property test:** decrypting `ct` with W + IV + AAD MUST recover the original private material; the tag MUST verify; any single-bit modification of `ct` or `iv` or `tag` MUST cause decryption to fail (AEAD integrity).

### TC02-04: Negative cases; modifications that MUST fail tag verification

**Purpose:** make the AEAD integrity property explicit; these are common implementer mistakes.

For TC02-01's envelope, the following modifications MUST cause tag verification to fail:

- Flipping any single bit of the ciphertext
- Flipping any single bit of the tag
- Flipping any single bit of the IV
- Decrypting with a wrong AAD (wrong file_id; wrong chunk_index; wrong `is_last`)
- Decrypting with the wrong DEK
- Decrypting with the wrong algorithm-version byte (the `0x01` at the start)

Each is an essential AEAD property; tests should explicitly cover them.

## Implementer notes

- **NIST SP 800-38D recommends 12-byte IVs for GCM.** 12 bytes universally; do not use other lengths (16-byte IVs are valid GCM but produce different ciphertexts and complicate cross-implementation interop).
- **Tag length is the full 16 bytes (128 bits).** GCM allows truncated tags; the format uses full 128-bit tags.
- **The tag is appended to the ciphertext** in the envelope layout (section 4.1). Some libraries return ciphertext plus tag concatenated (RustCrypto `aes_gcm` does); some return them separately. Implementers must place the tag in the correct envelope position regardless of library convention.
- **AAD is authenticated into the tag, NOT transmitted.** Both encrypt and decrypt sides must reconstruct the AAD identically. AAD construction is the most common cross-implementation bug source.
- **IVs MUST be unique per (key, ciphertext) pair.** GCM is catastrophically broken if an IV is reused with the same key. IVs are generated randomly per file (single-PUT) or derived via the HKDF chain from DEK plus chunk index (multipart); both ensure uniqueness.
- **The single-PUT envelope magic byte is 0x01** (envelope-format version), then 0x01 (algorithm version, AES-256-GCM). Multipart uses its own layout per section 4.2.

## Reviewer's verification path

Per test case, a reviewer:

1. (TC02-01 through TC02-03) Read the Envelope Format layout for the relevant envelope type.
2. Reconstruct the AAD from the spec.
3. Decrypt the published golden ciphertext with the published key + IV + AAD; verify the plaintext matches.
4. (TC02-04) Modify each bit position and confirm decryption fails.

A mismatch in step 3 indicates either a spec ambiguity (most likely the AAD construction) or an implementation bug.
