# Signet Drive: Canonical Test Vectors

These test vectors pin the canonical byte representations of cryptographic operations that any Signet Drive implementation MUST produce identically. This directory is the known-answer reference for anyone implementing or independently verifying the constructions in the published specifications.

## What this directory is for

1. **Cross-implementation byte agreement.** The web client (TypeScript plus WebCrypto), the `signet` CLI (Rust), and the server must all produce identical byte sequences for canonical operations. If any two diverge by a single byte, signatures and proofs fail to verify across components.

2. **Bug detection at build time.** Each test fixture catches its own class of bug at the moment the buggy code is written, not at integration time.

3. **Independent review fuel.** The vectors give any reviewer concrete reference values: compute this from the spec, then check whether your answer matches the published vector. Convergent answers mean the spec is unambiguous. Divergent answers mean an ambiguity to report; see the verification guidance in the repository README and SECURITY.md.

## Two-layer structure

Each category is organized as **Layer 1** (spec plus concrete inputs) and **Layer 2** (computed output bytes):

- **Layer 1:** for each category, concrete inputs (specific account ids, timestamps, key bytes), a reference to the spec section that defines the byte construction, and the expected-output structure. Where the operation is fixed by an external standard (NIST FIPS, IETF RFC), Layer 1 includes the actual byte values too.

- **Layer 2:** for the Signet-Drive-specific constructions, the reference implementation runs against the Layer 1 inputs and the output bytes are captured as golden files. Categories state their own fill status.

Hand-computed byte values from an untested implementation carry quiet correctness risk; Layer 2 values are only ever captured from tested code.

**ACVP vectors are consumed, not republished.** The ML-KEM-1024 and ML-DSA-87 implementations are validated in CI against NIST's published ACVP test sets (key generation, encapsulation, and decapsulation including implicit-rejection vectors; key generation, sign, and verify), fetched from NIST's own repository rather than copied here, since republishing NIST data adds no assurance. ## Conventions used throughout these specifications

**Byte encoding for documentation:**
- Hex strings: lowercase, no leading `0x`, no whitespace inside the string. Example: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.
- Inline emphasis on byte values: prefix with `0x`. Example: domain separator `0x00` for leaves, `0x01` for internal nodes.
- UTF-8 strings: shown as quoted strings; UTF-8-encoded bytes are inferred. Example: `"signet-drive-kem-wrap-v1"` is the 24-byte sequence `7369676e65742d64726976652d6b656d2d777261702d7631`.

**Integer encoding:** all multi-byte integers are **big-endian** unless explicitly noted otherwise. Standard widths: `uint8`, `uint16_be`, `uint32_be`, `uint64_be`. This matches RFC 6962, RFC 7518, and JOSE convention; little-endian appears nowhere in the format.

**Hash algorithm:** all hashes are **SHA-256** unless explicitly noted (none currently use a different hash). Output: 32 raw bytes (64 hex chars).

**Public key encoding:** ECDSA P-256 and ECDH P-256 public keys are X9.63 uncompressed format, 65 bytes total: `0x04 || X (32 bytes) || Y (32 bytes)`. Fingerprints are SHA-256 of the DER-encoded `SubjectPublicKeyInfo`, NOT the raw 65-byte X9.63 form.

## How to use these vectors

**As an implementer:**
1. Read the spec section referenced in each vector category.
2. Implement the canonical-byte construction in code.
3. Run your implementation against the Layer 1 inputs; compare against the Layer 2 expected outputs.
4. Treat any divergence as a bug: in the implementation, in the spec, or in a captured fixture.

**As an independent reviewer:**
1. Read the spec section referenced in each vector category.
2. Walk through the canonical-byte construction by hand, or via an independent implementation.
3. Compare your computed output to the Layer 2 expected output.
4. Match: the spec is unambiguous and the reference implementation is correct in this respect.
5. Mismatch: either the spec is ambiguous, or the reference implementation is wrong, or your interpretation is wrong. Report it (SECURITY.md for anything security-relevant; an issue otherwise).

## Update protocol

When an underlying spec changes, each vector's spec-source reference is checked and updated, the Layer 1 structure is reviewed for compatibility, and any Layer 2 fixtures the change invalidates are regenerated. Substantive changes are noted in release notes.
